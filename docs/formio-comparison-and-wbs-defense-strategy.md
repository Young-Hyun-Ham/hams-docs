# Form.io 비교 및 WBS 방어전략

## 1. 결론

고객 요청을 “Form.io와 동일하게 구현”이라는 한 문장으로 수용하면 범위가 무제한으로 확대된다. Form.io의 기능 목록은 폼 편집기뿐 아니라 AI 개발도구, 제출 데이터 플랫폼, 워크플로우, PDF/전자서명, 인증·권한, 멀티테넌시와 운영 인프라까지 포함한다.

따라서 제안과 WBS의 기준을 **제품 대 제품 복제**가 아니라 **고객 업무 시나리오 충족**으로 전환한다. 현재 제품은 AI 시나리오와 API 데이터 연계에 특화된 폼 빌더를 기준선으로 삼고, 부족 기능은 필수·선택·제외로 분리한다.

권고 계약 문구는 다음과 같다.

> 본 과업은 Form.io 제품 전체의 기능 동등성 또는 호환성을 보장하는 과업이 아니다. 합의된 컴포넌트, 업무 시나리오, API, 권한, 비기능 요구사항 및 수용 기준을 구현 범위로 한다. 비교표의 ‘미지원/부분 지원’ 항목은 별도 명시된 WBS에 한해 납품 범위에 포함한다.

## 2. 비교 판정 기준

| 등급 | 정의 | WBS 처리 원칙 |
|---|---|---|
| A: 현재 지원 | 현재 코드에서 핵심 사용자 흐름이 동작 | 기준선; 안정화·테스트만 산정 |
| B: 부분 지원 | 모델/UI/기반은 있으나 제품 수준 완결성이 부족 | 차이만 보완 산정 |
| C: 확장 가능 | 기존 구조를 재사용할 수 있으나 신규 구현 필요 | 별도 에픽·수용 기준 필요 |
| D: 신규 플랫폼 | 별도 서버, 보안, 운영 또는 외부 연동이 필요 | 본체와 분리한 옵션 과업 |
| X: 제외 권고 | 고객 업무 목적이 확인되지 않거나 비용 대비 효용이 낮음 | 기본 계약 범위 제외 |

## 3. Form.io 기능군별 비교와 방어 논리

### 3.1 AI 및 최신 개발 자동화

| Form.io 항목 | 현재 제품 | 등급 | 방어/대응 전략 |
|---|---|---:|---|
| MCP Server | 폼 빌더 모듈에는 없음 | D: 신규 플랫폼 | 폼 CRUD API를 먼저 안정화한 뒤 MCP는 별도 보안 채널·도구 권한·감사 요구사항으로 산정 |
| Agent Skills | 없음 | C: 확장 가능 | 제품 기능이 아니라 개발 생산성 자산. 고객 납품 범위와 분리해 템플릿/가이드 옵션으로 제시 |
| Agentic Coding Plugin | 없음 | D: 신규 플랫폼 / X: 제외 권고 | 특정 개발도구 종속 기능. 고객이 실제 운영 시나리오를 제시할 때만 별도 PoC |
| Universal Agent Gateway | 없음 | D: 신규 플랫폼 | 실행 권한, 컨텍스트, 데이터 접근 통제가 필요한 독립 플랫폼. 폼 빌더 WBS에 포함하지 않음 |

방어 포인트: AI 기능은 최종 사용자의 폼 작성 기능과 다른 계층이다. “AI를 사용한다”가 아니라 어떤 주체가 어떤 폼/API를 어떤 권한으로 생성·수정하는지 유스케이스를 요구한다.

### 3.2 폼 빌더 및 컴포넌트

| Form.io 항목 | 현재 제품 | 등급 | 방어/대응 전략 |
|---|---|---:|---|
| Drag & Drop Builder | 7종 요소 추가, 재정렬, 속성 편집, 미리보기 | A: 현재 지원 | 동등 주장 대신 고객 화면에 필요한 요소 목록으로 수용 기준 고정 |
| 앱 내 임베드/화이트라벨 | 기존 Builder 노드용 JSON 산출 구조는 있으나 범용 SDK는 미확인 | C: 확장 가능 | 대상 앱, 배포 방식, 테마, 인증 전달 규약을 별도 정의 |
| Premium/Custom Components | 중앙 레지스트리와 유형 메타데이터 기반 | B: 부분 지원 / C: 확장 가능 | 레지스트리 확장 단위로 신규 요소별 독립 산정; “무제한 커스텀” 제외 |
| Multi Page Wizard | 없음 | C: 확장 가능 | 페이지 모델, 이전/다음, 상태 유지, 분기, 오류 이동을 하나의 별도 에픽으로 산정 |
| Mobile Responsive | MUI 기반이지만 인증된 지원 기준 없음 | B: 부분 지원 | 지원 해상도·브라우저 매트릭스와 실기기 QA를 정의한 후 보완 |
| Accessible Forms | 일부 표준 UI 컴포넌트/ARIA 사용; 준수 검증 없음 | B: 부분 지원 / C: 확장 가능 | 목표 규격(KWCAG/WCAG), 등급, 검사 도구 및 수동 검수 범위를 명시 |
| CSS Customize | 테마 기반 UI이나 고객용 CSS 편집/SDK는 없음 | C: 확장 가능 | 허용 토큰 방식과 임의 CSS 방식의 보안·유지보수 차이를 분리 산정 |

방어 포인트: “컴포넌트 지원”은 이름이 아니라 상태, 속성, 검증, 접근성, 제출 데이터 형태, API 연계까지 포함한 수용 기준으로 계산한다.

### 3.3 데이터 처리 및 자동화

| Form.io 항목 | 현재 제품 | 등급 | 방어/대응 전략 |
|---|---|---:|---|
| JSON-Driven Forms | JSON 직렬화, 직접 편집, 정규화, 즉시 미리보기 | A: 현재 지원 | 현재 스키마를 기준 계약으로 지정; Form.io 스키마 호환은 별도 변환기 과업 |
| Validation/Conditional Logic | 검증 유형 설정 및 이벤트 기반 API 연계는 있으나 범용 규칙 엔진은 없음 | B: 부분 지원 / C: 확장 가능 | 1차는 필수/형식/범위, 2차는 표시·활성 조건, 3차는 워크플로우로 분리 |
| Auto Populate | API 응답을 대상 요소에 유형별 매핑 가능 | B: 부분 지원 | 합의된 API 응답 매핑 시나리오는 현재 강점으로 대응; 사용자 이력 기반 자동 채움은 별도 |
| Auto Save | 없음 | C: 확장 가능 | 저장 주기, 초안 보존기간, 재개 키, 실패 복구, 개인정보 정책을 먼저 확정 |
| Form Actions | 요소 이벤트→API→대상 반영은 지원; 제출 후 범용 액션은 없음 | B: 부분 지원 / C: 확장 가능 | 현재 “폼 내부 API 연계”와 신규 “제출 후 워크플로우”를 분리 |
| Offline Mode | 없음 | D: 신규 플랫폼 / X: 제외 권고 | PWA, 로컬 암호화, 동기화·중복 정책이 필요한 별도 과업; 현장 요구가 없으면 제외 |
| Collision Control | 없음 | D: 신규 플랫폼 | 폼 정의와 제출 데이터 각각의 동시성 정책이 다름. 버전 필드/낙관적 잠금부터 별도 산정 |

방어 포인트: 현재 제품은 API 연계와 응답 매핑에서 실질 기능을 갖는다. 범용 BPM/워크플로우 엔진까지 “조건부 로직”이라는 이름으로 묶지 않는다.

| CORS | 모듈 내 프로젝트별 설정 없음 | C: 확장 가능 | 인프라/API Gateway 정책으로 처리; 고객 UI 기능 요청과 분리 |

| Decoupled Updates | 저장 폼의 재편집은 가능; 발행 인스턴스 자동 반영 보장은 미확인 | B: 부분 지원 / C: 확장 가능 | 초안/발행, 버전 고정/최신 추종 정책을 먼저 결정 |
| Dynamic Translations | 편집기 UI는 i18n 기반; 폼 콘텐츠 번역 모델은 없음 | B: 부분 지원 / C: 확장 가능 | 편집기 번역과 고객 작성 콘텐츠 번역을 구분; 언어별 필드/번역 API 옵션화 |

## 4. 제안 범위 패키지

### 4.1 권고안: 업무 적합형 폼 빌더

다음 범위를 기본 납품으로 제안한다.

- 현재 7개 컴포넌트 기반 비주얼 편집, 재정렬, 속성 설정
- JSON 기반 저장/불러오기 및 서버 CRUD
- API 선택, 이벤트 호출, 요청 템플릿, 응답 경로 및 대상 요소 매핑
- 사용자별 컴포넌트 노출 정책
- 합의된 브라우저·해상도에서의 반응형 보완
- 필수값/기본 형식 수준의 검증 보강
- 기능 테스트, 오류 처리, 운영 문서

### 4.2 선택 옵션

| 옵션 | 포함 범위 | 선행 결정 |
|---|---|---|
| A. 다단계 폼 | 페이지 편집, 이동, 상태 유지, 페이지 검증 | 분기 필요 여부, 최대 페이지 수 |
| B. 조건부 규칙 | 표시/숨김, 활성/비활성, 값 계산 | 연산자와 참조 범위 |
| C. 초안/자동 저장 | 주기 저장, 재개, 만료, 실패 복구 | 사용자 식별, 보존기간 |
| D. 제출 액션 | 웹훅/메일 등 합의된 액션 | 재시도, 멱등성, 비밀정보 관리 |
| E. 버전 관리 | 초안/발행, 이력, 비교, 롤백 | 최신 추종 또는 버전 고정 |
| F. 접근성 | 목표 규격에 따른 개선/검증 | WCAG/KWCAG 등급과 검수 방식 |
| G. Export/PDF | 합의 형식의 제출 데이터 출력 | 템플릿 수, 대량 처리량 |

### 4.3 기본 제외 권고

- Form.io JSON/API와의 완전 호환
- 무제한 커스텀 컴포넌트와 무제한 외부 연동
- MCP/UAG/특정 AI 코딩 플러그인
- 법적 전자서명, PDF 시각적 디자이너, 범용 BI
- 오프라인 동기화, 멀티테넌시, 인증 영역, 범용 IAM
- 인증되지 않은 보안·접근성 규정의 포괄 준수 보장

## 5. WBS 산정안

아래는 범위 방어를 위한 **상대 규모 WBS**다. 실제 일정은 담당 인원, 백엔드 현황, 디자인 확정, 테스트 환경을 확인한 뒤 인일로 변환한다. 규모는 `S (소)`, `M (중)`, `L (대)`, `XL (별도 프로젝트)`로 표기한다.

### 5.1 Phase 0 — 범위 확정 및 기준선

| WBS | 작업 | 산출물/수용 기준 | 규모 | 기본 여부 |
|---|---|---|---:|---:|
| 0.1 | 고객 업무 시나리오 워크숍 | 사용자·입력·처리·출력 시나리오 목록 | M (중) | 필수 |
| 0.2 | 현재 기능 데모 및 Fit/Gap | 고객 확인 서명된 비교표 | S (소) | 필수 |
| 0.3 | 컴포넌트 카탈로그 확정 | 유형별 속성/검증/데이터 형식 | M (중) | 필수 |
| 0.4 | 비기능 요구 확정 | 브라우저, 성능, 보안, 접근성, 배포 기준 | M (중) | 필수 |

## 6. 범위 방어 체크리스트

고객의 각 요구사항은 개발 착수 전에 아래 질문에 답해야 한다.

1. 최종 사용자는 누구이며 어떤 업무 결과를 만들어야 하는가?
2. 폼 정의와 제출 데이터 중 어느 것을 저장·검색·감사하는가?
3. 필요한 컴포넌트의 개수와 각 속성·검증 규칙은 무엇인가?
4. 조건은 표시 조건인가, 값 계산인가, 승인 워크플로우인가?
5. 외부 API별 인증, 타임아웃, 재시도, 오류 처리, 호출량은 무엇인가?
6. 초안·발행·과거 버전 중 어떤 상태 모델이 필요한가?
7. 역할별로 폼 정의와 제출 데이터에 어떤 행위를 허용하는가?
8. 접근성·보안·전자서명은 어떤 공식 규격과 검수 증빙을 요구하는가?
9. 지원 브라우저, 모바일 기기, 동시 사용자, 응답시간 목표는 무엇인가?
10. Form.io 호환이 필요한가, 아니면 동일한 업무 결과만 필요한가?

답이 없는 항목은 “Form.io와 유사”라는 표현만으로 기본 범위에 편입하지 않는다.

## 7. 변경관리 원칙

- 비교표와 고객 수용 기준을 요구사항 추적표의 기준선으로 버전 관리한다.
- 신규 컴포넌트는 유형 하나가 아니라 UI, 속성, JSON, 검증, 미리보기, 저장, 접근성, 테스트를 묶은 단위로 변경 요청을 산정한다.
- 외부 서비스 연동은 서비스별 인증·오류·재처리 차이가 있으므로 액션 종류별로 별도 산정한다.
- 법적/규정 준수 표현은 목표 규격, 시험 주체, 증빙 산출물이 계약에 명시된 경우에만 사용한다.
- PoC는 기술 가능성 검증이며 운영 품질, 보안, 성능, 유지보수까지 포함하지 않는다고 명시한다.
- 고객이 Form.io의 신규 기능을 추가 비교 대상으로 제시하면 자동 포함하지 않고 영향 분석과 변경 승인을 거친다.

## 8. 데모 및 협상 순서

1. 현재 빌더에서 컴포넌트를 드래그해 폼을 만든다.
2. JSON을 수정해 미리보기에 즉시 반영되는 것을 보여준다.
3. API 이벤트가 다른 요소의 값·옵션·그리드를 채우는 흐름을 시연한다.
4. 저장 후 검색·재로드하여 JSON과 UI가 유지됨을 보여준다.
5. 고객의 실제 업무 시나리오를 같은 흐름으로 매핑한다.
6. 충족되지 않는 항목만 옵션 WBS에서 선택하게 한다.

이 순서는 기능 개수 경쟁을 피하고, 이미 구현된 API 중심 폼 구성 역량과 고객 업무 적합성을 먼저 증명하는 데 목적이 있다.
